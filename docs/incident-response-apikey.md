# APIキー漏えい時の対応手順（インシデントレスポンス）

Stripe の APIキー（または APP_KEY・セッション等）が漏えいした / した可能性がある場合の対応を、
**攻撃者・主催者(ユーザー)・管理者(プラットフォーム)・法務** の各視点から整理する。
まず「何が起き得るか（攻撃者視点）」を把握し、被害を止め、範囲を確定し、通知・再発防止まで行う。

前提（本システムの設計）:
- Stripe鍵は**主催者ごとに分離**して暗号化保存（AES-256-GCM / APP_KEY）。漏えいは原則その主催者1アカウントに限定。
- 参加者PII（氏名・メール・電話）は**当サービスDBに保存せず、各主催者のStripe内**にある。
- 監査ログ `logs/audit.log`（＝`dirname(DB)/audit.log`）に鍵操作・返金・CSV出力・越権拒否・ログイン等を記録。

---

## 漏えい時に起こり得ること（影響範囲の早見表）

### 影響が及ぶ範囲
- **その鍵を登録した主催者1人の Stripe アカウントのみ**。他の主催者・当サービス全体・他アカウントには波及しない（鍵は主催者ごとに分離）。
- 参加者PII（氏名・メール・電話）はサーバーDBに無く、その主催者の Stripe 内にある。影響もその範囲。

### 起こり得ること（鍵の種類で変わる）
| できること | `rk_`（推奨・権限を絞る） | `sk_`（フルアクセス） |
|---|---|---|
| 参加者名簿の閲覧（氏名・メール・電話・支払状況） | 付与すれば可 | 可 |
| 返金の実行（残高→支払者へ戻る＝資金流出・妨害） | 付与範囲のみ | 可 |
| Checkout / PaymentIntent 等の作成 | 付与範囲のみ | 可（ただし下記） |
| **別口座への送金・入金先(銀行)の変更** | ❌ 不可（Payouts / External accounts を付与しない） | ⚠️ 触れる権限あり＝リスク大 |
| 不正 Webhook 追加で以後のイベントを横流し | 付与範囲次第 | 可 |
| 財務データ（売上・残高）の閲覧 | 付与範囲次第 | 可 |

- **test キー**：すべてテスト環境のみ（実在の顧客・実際の金銭は動かない）。**live キー**：実データ・実際の金銭が対象。

### 起こら「ない」こと
- カード番号そのものの取得（Stripe が保持・誰も見られない）。
- 他人のカードへ勝手に課金（本アプリはカードを再利用保存していない＝`setup_future_usage` 未使用。任意カード課金にはカード番号が必要）。
- `rk_`（推奨構成）での送金・入金先変更（権限に含めないため不可）。
- 他サービス（メール・銀行・サーバー・当サービス管理画面）への侵入（Stripe 専用の鍵）。
- 当サービスの Webhook 偽装（署名シークレット whsec が別途必要）。

### 「本当にお金が抜かれる」筋道
- 攻撃者が利益を得る現実的な道は **残高を別口座へ送金（Payout 乗っ取り）** のみ。これは `sk_`（フルアクセス）のリスクで、**推奨の `rk_`（Payouts / External accounts を付与しない）なら塞げる**。
- 「請求してお金を入れる」は入金先が主催者本人なので攻撃者の得にならず無意味。

### 二次被害（別システムへの波及）
- 鍵自体は他システムを開けないが、**盗んだ参加者PII が外部でフィッシング・詐欺・クレデンシャルスタッフィングに使われる**恐れ → 漏えい時は参加者への注意喚起が必要。

### 一言で
- 最悪の `sk_live` でも「その主催者の名簿流出＋返金/オブジェクト作成、送金乗っ取りのリスク」まで。カード番号・他者データ・他サービスには及ばない。
- **推奨の `rk_` にすれば、送金・口座変更まで封じられ、被害は「名簿閲覧・返金」程度に限定できる。**

## 0. 最初の30分（共通・最優先）
1. **鍵を失効(Roll)**：Stripe ダッシュボード →「開発者」→「APIキー」で該当キーを Roll（無効化＋再発行）。これで攻撃者のアクセスは即遮断される。
   - どの鍵かは、当サービスの監査ログの `stripe.key.save ... fp=XXXX`（末尾4桁）で照合できる。
2. **当サービスで差し替え**：Stripe設定画面で新しい鍵（できれば `rk_` 制限付き）に登録し直す。
3. **証拠保全**：`audit.log`、サーバーのアクセスログ、Stripe の「開発者 → ログ/イベント」をこの時点の状態で保存。

---

## 1. 攻撃者の視点（＝先回りして潰す／確認する）
漏れた鍵で攻撃者がやり得ること：
- **参加者データの吸い出し**（顧客一覧＝氏名・メール・電話・支払状況）→ フィッシング等の二次被害。
- **返金・顧客作成などの操作**（フルアクセス鍵 `sk_` の場合。`rk_` なら付与権限内に限定）。本番鍵なら実際の返金が動く。
- **永続化**：不正な Webhook エンドポイント追加、（可能なら）追加のAPIオブジェクト作成。
- ※ **カード番号そのものは取得不可**（Stripe が保持・鍵所有者も見られない）。**payout先（入金銀行口座）変更は通常APIキー単体では不可**（ダッシュボード認証が必要）。

→ 確認すべきこと（Stripe ダッシュボード）:
- 「開発者 → ログ」で、漏えい期間に**どのAPIが叩かれたか**（顧客一覧取得・返金など）。
- 「開発者 → Webhook」に**身に覚えのないエンドポイント**が無いか（あれば削除）。
- 「返金」「支払い」に**不審な操作**が無いか。
- 「チームメンバー」「APIキー」に**不審な追加**が無いか。

---

## 2. 主催者（ユーザー）の視点
自分のStripe＝自分の参加者データが対象。やること：
1. 上記「最初の30分」を実施（Roll → 差し替え）。
2. **Stripeアカウント自体の保護**：ダッシュボードのパスワード変更＋Stripeの2段階認証を有効化。
3. **今後は制限付きキー(rk_)** を使う（漏えい時の被害を最小化）。当サービスのStripe設定画面に rk_ の作り方ガイドあり。
4. **影響範囲の特定**：Stripeログから、漏えい中に参加者名簿が読み出された形跡があるか確認。
5. **参加者への通知**（PIIが読まれた可能性がある場合）：氏名・メール・電話が漏れた可能性を対象者へ連絡し、不審な連絡に注意喚起。

---

## 3. 管理者（プラットフォーム）の視点
最重要判断：**「1主催者の鍵だけ」か「サーバー侵害（＝全主催者の鍵が危険）」か**。

### 3-1. 1主催者の鍵のみ
- 当該主催者に本手順を案内。プラットフォーム全体の対応は不要。監査ログで越権が無いか確認。

### 3-2. サーバー侵害の疑い（.env / 鍵ファイル / DB が読まれた等）
全主催者の鍵・APP_KEY・セッションが危険。以下を実施：
1. **全セッション失効**：`php bin/console.php revoke-sessions` → 全員再ログイン。
2. **APP_KEYローテーション**：`php bin/console.php rotate-app-key`
   - 現行キーで全秘密を復号し、新APP_KEYで再暗号化する。実行前に `data/` をバックアップ。
   - APP_KEY を実環境変数で運用中なら、出力された新キーを環境変数にも設定する。
3. **全主催者へ通知**し、各自の **Stripe鍵を Roll → 再登録**してもらう（サーバー上の鍵は漏れた前提で無効化）。
4. **サーバーの健全性確認**：改ざんファイル・不審なcron・`.env`のアクセス痕跡・`.htaccess`が有効か。必要なら**クリーンな環境へ再構築**し、コードを再デプロイ。
5. **恒久対策**：APP_KEY を `.env` ではなく実環境変数へ、`STRIPE_CONNECT_REQUIRED=1`（鍵を持たない）や `rk_` への移行を検討。

### 監査ログの見方（`audit.log`）
- `stripe.key.save/clear`：鍵の登録・削除（`type`=full/restricted、`fp`=末尾4桁）。
- `refund` / `csv.export` / `onsite.*` / `attend`：主催者操作。
- `authz.deny` / `csrf.fail` / `login.*` / `login.2fa.fail`：不正・越権の試行。
- 時刻・IP・UA が付くので、**不審なIP/UAからの操作**を洗い出せる。

## 4. 法務・コンプライアンスの視点（日本）
- 参加者PII（氏名・連絡先）の漏えいは、**個人情報保護法**上の対応対象になり得る。
  - 一定の要件（要配慮情報・大規模・不正目的等）に該当する場合、**個人情報保護委員会への報告**と**本人通知**が必要。
  - 該当有無を早期に判断し、**時系列・影響範囲・対応内容を記録**しておく。
- 決済・返金に不正があった場合は Stripe／カードブランドの手続きにも留意。

## 5. 復旧後（再発防止のチェック）
- [ ] 漏れた鍵は Roll 済み・新鍵(できれば rk_)に差し替え済み
- [ ] 不審な Webhook / APIキー / チームメンバー / 返金が無いことを確認
- [ ] （サーバー侵害時）revoke-sessions・rotate-app-key 実施、全主催者に再登録依頼
- [ ] APP_KEY を実環境変数へ、鍵ディレクトリは公開領域外
- [ ] 影響を受けた参加者へ通知（必要な場合）、記録を保全
- [ ] 原因（どこから漏れたか）を特定し、経路を塞いだ
